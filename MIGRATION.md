# Go CLI and multi-server migration

## Required outcome

- Replace the TypeScript client with a Go executable, including build, installation and release workflows.
- Load commands at runtime from `$DECX_HOME/cli.json` (default `~/.decx/cli.json`); register server commands under engine namespaces (`decx jadx …`, `decx asc …` and `decx kuna …`) and expose local workflows through runtime plugins behind the global `--plugin <id>` selector (`decx --plugin ard-framework …`), with `decx session …` built in. Embed and install the shipped configuration without overwriting user changes. Final design: `cli.json`, the embedded defaults and `self init` were removed in favour of self-describing `decx.json` manifests discovered under `$DECX_HOME` and in source checkouts, with a compiled-in known-module table carrying the release sources of the shipped modules; engine namespaces and the `--plugin` selector were later collapsed into one module surface (`decx -m <module> <command>`, see the module entry under Implementation status).
- Keep tool domains separate from server implementations. The session manager owns server selection, target identity, launch, readiness, reuse, process termination and persistent records.
- Support the Kotlin `jadx-server` (renamed from the original server at the user's request), a Rust `kuna-server` and a Python `asc-server`, using actual upstream analysis capabilities.
- Ship a unified configuration covering the supported tools and preserve Android device/framework workflows during the client migration.
- Verify configuration-driven invocation, real process lifecycle, each real analysis backend, and installation from a clean home.

## Evidence and design references

- `decx-cli-dev:decx-cli/config.json` and its session modules separate tool domains from engines. That branch compiles configuration into Rust; the new Go implementation must instead load it at runtime.
- OpenCLI: https://github.com/jackwener/opencli — extensible command registry and a unified entry point. No browser dependency is needed for DECX server calls.
- Kuna: https://github.com/Noelo-Lab/kuna — Rust workspace under `decompiler/`; real function decompilation must be used rather than presenting disassembly as recovered source.
- ASC: https://github.com/MG1937/ASC — Python `getclass` and `findrefs` capabilities; do not advertise unsupported JADX endpoints as ASC capabilities.

## Implementation status

This branch is Go-only: the TypeScript client sources have been removed, `decx` (the Go CLI) builds the executable (`go build ./cmd/decx`) and each component publishes from its own release workflow (`.github/workflows/release-cli.yml` for the CLI archives, `release-jadx-server.yml`, `release-asc-server.yml`, `release-kuna-server.yml` and `release-ard-framework.yml` for the analyzers and the plugin). The published npm package still serves the last TypeScript release, so the top-level `README.md`/`README_zh.md` keep documenting that older surface until the next tagged release switches them over.

- Implemented: runtime registry, schema validation, request mapping, dynamic Go command help and HTTP invocation. The first iteration embedded JADX defaults in `cli.json` and had `self init` install them without overwriting a user registry; the final registry deleted both and loads self-describing `decx.json` manifests instead (see the engine-first entry below).
- Implemented: `decx self skills install` — the Go port of the removed TypeScript skills installer. It clones `https://github.com/jygzyc/decx.git` (or uses a local source override), stores every `decx-*` skill that carries a `SKILL.md` under `$DECX_HOME/skills`, and links them into `~/.codex/skills`, `~/.claude/skills`, `~/.cursor/skills` or the shared `~/.agents/skills` (the default). Links are symlinks with a Windows junction/copy fallback; `decx/internal/skills` has unit tests and `internal/cli` covers the command end to end with a fixture source.
- Implemented: engine-first command registration and optional engine installation. `decx <engine> <command>` runs server commands, `decx --plugin <id> <command>` runs plugin workflows, and `engine list`/`plugin list` report every component with its install state and version. The registry is manifest-driven and deliberately offers no backward compatibility: `cli.json` and its catalog concept were deleted, and each component ships its own `decx.json` manifest (runtime definition, release source and command tree) and `VERSION` file, installing under `$DECX_HOME/bin/<id>` (servers) or `$DECX_HOME/plugins/<id>` (plugins); a component is runnable only once its manifest is found on disk, and the nearest `modules/` (servers) or `plugins/` (plugins) directory above the `--config` path, the executable or the working directory is discovered for development. A compiled-in known-component table supplies the `jadx`/`asc`/`kuna`/`ard-framework` release sources for components that are not installed; `decx install`/`decx self update` resolve the newest release that actually ships a matching asset, verify the SHA-256 from the release's `SHA256SUMS`, extract the archive into a staging directory and swap it in, and skip artifacts whose installed `VERSION` already matches. Plugins use the same path, are installed when selected (`--plugin <id>`, `--all`) or when the known table marks them default — the `ard-framework` plugin is. Asset templates take `{version}` plus the platform tokens `{os}`/`{arch}` (Go `runtime.GOOS`/`GOARCH` values), so a component can ship per-platform archives under one release.
- Verified: plugin installation against a stub release server — `decx install --plugin jadx-gui` downloads into `$DECX_HOME/plugins`, `plugin list` reports the installed version, and a plain `decx install`/`decx self update` never fetches plugins that are not installed. The real `jadx_decx_plugin-{version}.jar` asset appears once the updated release workflow runs.
- Verified: clean-home end-to-end install. With `DECX_HOME` pointing at an empty directory, `decx install` resolved v4.2.0 through the `decx-server-{version}.jar` fallback asset, downloaded it to `$DECX_HOME/bin/jadx-server.jar`, `decx session open tests/fixtures/sieve.apk` launched it successfully, `decx jadx classes --session … --limit 3` returned classes, and `decx session close --all` left an empty session list.

- Implemented: persistent Go session manager and `session open/list/check/close`, engine-compatible auto-selection and `--session`, random ports, launch/script identity, OS store locking, atomic records, readiness heartbeat, timeout retention and PID/creation-time verification before termination. Tests use actual helper server processes, including concurrent opens and mismatched process identity.

Keep runtime JAR copies separate from Gradle output to avoid rebuilding a live classpath during verification.
- Verified: Windows amd64 and Linux amd64 Go cross-builds; this proves compilation, not runtime behavior on those platforms.
- Implemented and verified: Kotlin module renamed to `modules/decx-jadx`, entry point `JadxServerApp`, `jadx-server` JAR/release references, and default Go engine ID `jadx` with `DECX_JADX_SERVER` override. `./gradlew :jadx-server:shadowJar :jadx-server:dist` succeeds; the JAR help names JADX Server and demonstrates `decx jadx classes --port`.
- Implemented: engine-first command registration with runtime plugins. Server commands live on engines (`decx <engine> <command>`); runtime plugin commands live on the plugin's `commands` tree in its `decx.json` manifest and are reached with the global selector flag (`decx --plugin <id> <command>`). A plugin is one self-contained JavaScript file (`entry`) evaluated in-process by the CLI's embedded QuickJS engine (`quickjs-go`, linked through cgo) and called as a global `handle(request) -> response`, with the host exposing a `decx` global carrying `fs`/`path`/`os`/`child_process`/`crypto`, a `Buffer`/`TextEncoder`/`TextDecoder` prelude and `console` bridged to stderr — no module loader, no Node or npm toolchain on any platform. `engine list` and `plugin list` report each discovered component with its install state and release source, and engine and plugin names share one reserved namespace (`session`, `engine`, `plugin`, `self`, `install`, `settings`, `help`). Engines can only expose HTTP-routed commands.
- Implemented: the plugin engine is QuickJS (`github.com/buke/quickjs-go`) instead of goja, so the `decx` binary is linked through cgo: a C toolchain is required to build it, `decx/cmd/pack` only packs the platform it runs on and `.github/workflows/release-cli.yml` builds each archive on a native runner (linux/darwin/windows, amd64/arm64), merging the per-platform `SHA256SUMS` in a publish job.
- Implemented and verified: `cd decx && go build ./... && go test ./...` plus manual runs of `decx --help`, `decx jadx --help`, `decx engine list`, `decx plugin list` and `decx --plugin ard-framework device system-services` (reports `ADB_DEVICE_MISSING` without a device).
- Implemented: Android device and framework workflows as the `ard-framework` plugin under `plugins/ard-framework` (authored in TypeScript, bundled by esbuild into the single file `dist/ard-framework.js`) — `decx --plugin ard-framework device system-services|permission-info` and `decx --plugin ard-framework framework collect|process`. The plugin talks to adb, collects from `/system/framework` plus `/apex`, extracts dex, processes APEX payloads and packs jars; it only reports the packed jar path, and `decx session open` opens it, so process ownership stays in the CLI. No native binaries are packaged by the CLI.
- Implemented: JADX argument normalization lives in the server (`JadxPassthroughArgs`, jadx-server), so every client sends only `[target, --port, <user jadx flags>, <scripts>]`. It drops `--deobf`, defaults `--show-bad-code`, `--no-imports`, `-Pdex-input.verify-checksum=no` and `--rename-flags case,valid`, strips the `printable` rename token and rewrites `all` to `case,valid` while leaving `none` and unparseable values to jadx. It also canonicalizes the DECX `-rf` alias to jadx's `--rename-flags`: jadx 1.5.6 only declares `--rename-flags`, and with `acceptUnknownOptions(true)` a surviving `-rf` would land in the input-file list. Verified by 19 unit tests plus a healthy server start with `--deobf --rename-flags all`.
- Removed: the Go native Android implementation (`decx/internal/android`), the packaged `decx/native-tools` erofs binaries and the `dist/bin.tar.gz` packaging. Framework/device logic lives in the plugin instead; payload images are parsed natively in JavaScript (ext4 reader plus an EROFS reader ported from the Rust branch's `android_sdk/erofs.rs`) and system `debugfs`/`extract.erofs`/`fsck.erofs` from `PATH` (or `DECX_DEBUGFS`/`DECX_EXTRACT_EROFS`/`DECX_FSCK_EROFS`) serve only as the fallback for unsupported payload features — no WSL delegation. CLI archives no longer carry the plugin tree: the plugin release workflow (`.github/workflows/release-ard-framework.yml`) builds the plugin and attaches the platform-independent `decx-ard-framework-plugin-{version}.zip` to the release, and `decx install`/`decx self update` extract it under `$DECX_HOME/plugins/ard-framework`, which is where the CLI loads the bundle from. Publishing is not the CLI's responsibility; the CLI only parses the registry and loads the installed bundle.
- Implemented: archive-based component installation, now the only install path. Every component ships a `decx.json` manifest + `VERSION` file inside its `zip`/`tar.gz` (or in a local directory), so the CLI always installs a directory tree: the archive is extracted into a staging directory next to the destination and swapped in only after the manifest validates (kind/id/entry) and the SHA-256 from `SHA256SUMS` matched, so a broken download leaves the previous install untouched; repeat installs of the same release skip the download. Both the ASC source zip and the Kuna platform archives consume this path, as does the `ard-framework` plugin bundle.
- Pending: publish the renamed `jadx-server-*.jar` asset in an actual release (the workflow already produces that name) and verify the remaining build targets at runtime.
- Implemented: registry defaults, local installs and graceful stop commands. The first iteration put a `release` section in `cli.json` (`repository` defaulting to `jygzyc/decx`, opt-in `prerelease`) that every component without its own `repository` inherited, and an `install` block could use `"source": "local"` with `path` to install an archive or directory already on the machine. The final registry deleted `cli.json`: the default repository now lives in the compiled-in known-module table (`decx/internal/registry/known.go`) and every manifest's own `release` block overrides it, prereleases are selected with the `--prerelease` CLI flag, and the manifest schema no longer accepts a local `path`, so components install from repository releases. Modules declare how they stop with `launch.stop`: `"terminate"` is the default, a command list runs first for a graceful shutdown (`{pid}`, `{port}`, `{binary}`, `{home}`, `{target}` substituted) and the CLI terminates the process anyway when the command fails or the server survives it.
- Pending: verify the framework plugin on Linux and Windows (native ext4/EROFS readers; the PATH-only `debugfs`/erofs-utils fallback does not exist on Windows, so unsupported payloads are expected to fail with guidance there); the removed Go implementation's fixture-based ext4 tests now have JavaScript equivalents, and the EROFS reader carries the Rust branch's byte-exact fixture (`apex_payload_erofs.img`).
- Implemented: `decx self update --cli` replaces the running executable with the newest `decx-cli-{version}-{os}-{arch}` release archive (`tar.gz` on Unix, `zip` on Windows). The download is extracted next to the executable and swapped in only after it succeeded, so a failed update leaves the previous binary in place; the replacement is skipped when the running version already matches, `--force` overrides it, `--prerelease` selects prereleases and a `go run`/temporary executable is refused with an explanatory error. Covered by `internal/install` helpers plus a CLI test that swaps a stand-in executable against a stub release server.
- Implemented: ASC vendored as the git submodule `modules/decx-asc/asc` (pinned gitlink `ccc6bae…`) with a rewritten `modules/decx-asc/asc_server.py` that imports the upstream client API from the submodule tree (`sys.path` + `asc/` discovery: sibling dir, submodule name, `ASC_ROOT`, `--asc-root`, ancestor walk). `bin/asc-server` bootstraps a venv from `asc/requirements.txt` and execs the adapter; `build.sh` packs `dist/asc-server-<release-version>.zip` (`decx.json`, `VERSION`, `bin/asc-server`, `asc_server.py`, `asc/`, `UPSTREAM.md`) without touching the submodule and the `asc-server-v*` workflow publishes it. Verified end to end against the Sieve fixture APK: `get_class_source` and `find_refs` return real ASC output, both via the staged archive directly and through the Go client (`decx session open --engine asc` → `decx asc class-source|find-refs` → `decx session close`), with the engine resolved from `$DECX_HOME/bin/asc/bin/asc-server`.
- Implemented: Kuna vendored as the git submodule `modules/decx-kuna/kuna` (pinned gitlink `92d952d1…`, Apache-2.0) with a Rust server crate at `modules/decx-kuna/server/` that links the upstream `decompiler/` workspace crates (`kuna-console`, `kuna-analysis`, `kuna-decomp`, `kuna-base`) and drives them in-process instead of shelling out: one bootstrap per process, then `get_functions` (function inventory), `get_function_source` (pseudo-C for one function by name or address) and `get_function_xref` (callers/callees) over a stdlib HTTP/JSON layer (upstream ships no HTTP or serde stack). `kuna/specs` is compiled once by the submodule's `slacomp` into a copy (never into the submodule) and shipped inside the archive; `build.sh` packs `dist/kuna-server-<release-version>-<os>-<arch>.zip` (layout `bin/kuna-server`, `kuna_server`, `specs/`, `LICENSE`, `NOTICE`, `UPSTREAM.md`) using Go's `runtime.GOOS`/`GOARCH` platform names so the registry's `{os}`/`{arch}` asset template resolves directly. The registry installs it under `$DECX_HOME/bin/kuna` (manifest `binary: bin/kuna-server`, env `DECX_KUNA_SERVER`) through the `kuna-server-v*` workflow.
- Implemented: modules replace engines and plugins. The first iteration registered server commands under engine namespaces (`decx <engine> <command>`), plugin workflows behind the global `--plugin <id>` selector, and reported discovery with `engine list`/`plugin list`; the final surface treats every server and plugin as one **module** selected with the global flag — `decx -m/--module <module> <command>`, with `decx -m <module>` alone printing the module's command list — and reports with `decx module list` (one JSON row per module: `id`, `kind`, `description`, `default`, `installed`, `path`, `version`, `installable`, `source`). All modules install under the shared `$DECX_HOME/modules/<id>` root (servers were under `$DECX_HOME/bin/<id>`); `decx install --engine/--plugin` became `decx install --module <id|repo|path>`, where the source is classified in order as a known module id (release install, SHA-256 verified as before), an existing directory or `.zip`/`.tar.gz` archive (imported), or a repository (`owner/repo[@ref]`, `github.com/owner/repo`, `https://host/owner/repo` — default branch resolved through the API, archive downloaded and imported); repo and path imports record their origin in `<module>/.decx-source.json` so `decx self update` re-imports from the same place, while a release install clears the record. `decx session open --engine <id>` still selects which server module backs a session, and `--config <dir>` still adds an extra scan root (its `modules/`, plus the legacy `bin/`/`plugins/` layouts). A module that is not installed answers ``module <id> is not installed; run `decx install --module <id>` ``, and an unknown selector answers `unknown module "<id>"; see module list`.
